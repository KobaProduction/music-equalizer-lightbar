# WS2812B behavior recovery and transport

## Board mapping

On `Music-Light-V3-221101`, continuity tracing and hardware execution confirm:

- 32 addressable RGB LEDs;
- one-wire WS2812-compatible behavior;
- data signal on ST17H66B **P34 / TSSOP-16 pin 1**.

## Recovered factory behavior contract

Behavior recovery of the preserved original firmware identified the complete LED SPI action route and its transport contract.

Factory SPI configuration:

- SPI controller: **SPI1**
- MOSI: **P34**
- SCLK / SSN / MISO: dummy/unrouted pins
- requested baud: **3,000,000 Hz**
- SPI mode: **MODE1**
- data-frame size: **8 bit**
- TX DMA: **enabled**
- RX DMA: disabled
- interrupt mode: disabled
- force-CS flag: enabled
- transmit path: PHYplus `hal_spi_transmit`

The factory PHYplus clock formula is used unchanged:

```text
divider = (pclk + baud/2) / baud
```

It does **not** force the divider to an even value.

With the observed runtime PCLK of 16 MHz:

```text
requested baud = 3.0 MHz
divider        = 5
effective baud = 3.2 MHz
SPI bit time   = 312.5 ns
```

## Recovered pixel encoding

The factory LED encoder expands each LED bit into four SPI bits:

| LED bit | SPI symbol | At 3.2 MHz |
| --- | --- | --- |
| 0 | `1000` | HIGH ≈ 312.5 ns, LOW ≈ 937.5 ns |
| 1 | `1110` | HIGH ≈ 937.5 ns, LOW ≈ 312.5 ns |

Two LED bits are packed into each SPI byte:

- `00` → `0x88`
- `11` → `0xEE`

The recovered action node processes three input color bytes per pixel in the order:

```text
input[1], input[0], input[2]
```

For the project RGB representation this is **GRB wire order**.

Per pixel:

- 24 LED bits;
- 96 SPI bits;
- **12 SPI bytes**.

For 32 LEDs:

- **384 SPI bytes** per frame.

The factory encoder does **not** append zero-filled reset bytes to the SPI payload. The line remains low between independently submitted frames, which provides the latch/reset interval.

## Implementation

The validated backend intentionally follows the recovered factory behavior contract rather than a generic WS2812 timing approximation:

```text
RGB frame
  -> GRB ordering
  -> 4-bit expansion (0=1000, 1=1110)
  -> 384-byte frame for 32 LEDs
  -> stock PHYplus SPI1 + TX DMA path
  -> P34
```

The project uses the vendor PHYplus SPI driver for this action route instead of maintaining a parallel direct-register DMA implementation.

## Hardware proof

Hardware validation on the actual `Music-Light-V3-221101` board passed with source commit:

`710c98281333e61224ca7799f9f393af9590fd0f`

The diagnostic frame used:

- all 32 LEDs;
- raw channel level `1`;
- LEDs 0..10 green;
- LEDs 11..20 red;
- LEDs 21..31 blue;
- immutable 384-byte encoded frame;
- repeated approximately every 20 ms.

Observed result: **the LED chain operated correctly**.

Validation level for the recovered LED transport: **hardware-pass**.

This hardware result supersedes the earlier experimental 2.4 MHz / 3-bit and 4 MHz / 5-bit SPI encodings.
